# Проект

Прототип информационной системы учёта выращивания культур (часть будущей системы учёта мясокомбината).

## Стек

- AdonisJS v6
- Edge SSR
- SQLite через better-sqlite3
- Session auth
- npm

## Ограничения архитектуры

- Не делать SPA.
- Не делать отдельный REST API без необходимости.
- Клиентская часть: серверный рендеринг, формы, Edge-шаблоны, минимум JS (Alpine.js при необходимости).
- Изменения БД только через миграции (`node ace make:migration`), без ручных правок схемы.
- Не использовать внешние очереди, микросервисы, Redis, Docker.
- Приложение должно запускаться на shared-хостинге с Node.js.
- Не вводить сущности/таблицы, которых нет в согласованной модели данных (см. ниже), без явного обсуждения.

## Архитектурные принципы

- Бизнес-логика (расчёты, рекомендации, правила совместимости) — в `app/services/`, не в контроллерах и не в моделях.
- Контроллеры — тонкие: валидация входа → вызов сервиса → рендер Edge-вьюхи или редирект.
- Связи между моделями — через Lucid `@belongsTo`/`@hasMany` + реальные FK-колонки (`field_id`, `crop_id` и т.д.), без денормализации данных, которые можно получить запросом (например, "история посевов" — это выборка Seeding по field_id, а не отдельное поле).
- Значения, которые представляют собой факт "на момент события" (себестоимость посева, вероятность урожая на момент выбора), сохраняются как снапшот в таблице события (Seeding), а не пересчитываются на лету от текущих цен справочника.
- Значения, отражающие текущее состояние (статус поля, наличие активного посева), не дублируются — проверяются запросом или простым флагом, обновляемым в момент события.

## Модель данных (актуальная, менять только по согласованию)

- Field: площадь, тип, статус, название (опционально, для отображения — иначе «Поле №N»)
- Crop (справочник): название, семейство, цена, средний урожай на га
- Fertilizer (справочник): название, цена
- Seeding (посев): field_id, crop_id, площадь посева (снапшот, не больше площади поля), начало/конец, статус, урожай (факт), себестоимость (снапшот)
- SeedingFertilizer: seeding_id, fertilizer_id, stage_name, dosage_used

## Права доступа

- Все аутентифицированные пользователи равноправны — ролей и RBAC нет и не планируется в рамках прототипа. Любой залогиненный пользователь видит и редактирует все данные. Это осознанное решение, а не недоработка.

## Что НЕ делать без явного запроса

- Не добавлять аутентификацию через сторонние OAuth-провайдеры — только Session auth.
- Не вводить ORM/query-паттерны, требующие raw SQL, если Lucid справляется.
- Не предлагать вынос справочников (Crop/Fertilizer) в отдельный сервис/БД — это часть одной SQLite-базы.
- Не проектировать "на будущее" под несуществующие пока модули (мясокомбинат, корма) — только текущий модуль выращивания.
- Не усложнять расчёт вероятности урожая — используется простое правило на основе совместимости с почвой и историей поля, без ML/весовых моделей, если не оговорено отдельно. Фактическое правило: два бинарных фактора — семейство культуры не совпадает с семейством предыдущей культуры поля (севооборот) и тип почвы поля входит в список подходящих почв семейства. Оба фактора выполнены — вероятность высокая, один — средняя, ни одного — низкая. Таблица подходящих почв — `app/constants/crop.ts` (`PREFERRED_SOILS`).

## Стиль кода

- TypeScript strict, без `any` без необходимости.
- Именование таблиц/колонок — snake_case (Lucid camelCase-маппинг в моделях по умолчанию).
- Всякая новая сущность добавляется по цепочке: migration → model → controller → routes → Edge views (см. пример ниже).
- Не оставлять комментарии в коде — ни поясняющих, ни JSDoc, ни TODO. Имена сущностей и структура кода должны объяснять происходящее сами; если без комментария непонятно, переписывается код, а не добавляется текст.
